# Методика тестирования обработки научных публикаций

**Область уточнена:** 30 июля 2026 года

**Назначение:** репозиторий воспроизводимых тестов библиотек, инструментов, приложений и skills, которые обрабатывают уже имеющиеся научные материалы.

## 1. Граница проекта

Корпус заранее предоставлен исследователем и доступен через Zotero MCP.

Обработка выполняется текущим Codex-агентом или локальной LLM. Передача текста корпуса внешним модельным API запрещена. Сетевой доступ, если он нужен для загрузки кода или документации тестируемого компонента, отделяется от запуска на корпусе.

Допустимые входы:

- библиографические метаданные Zotero;
- полный текст статьи в HTML;
- PDF, если HTML отсутствует или недостаточен;
- заметки, аннотации и выделения Zotero;
- заданный исследователем набор статей или коллекция Zotero;
- для итоговой исследовательской статьи — протокол, таблицы результатов, рисунки, подписи и другие утверждённые материалы исследования.

Допустимые выходы:

1. Ответ на вопрос по предоставленному корпусу.
2. Литературный обзор по предоставленному корпусу.
3. Итоговая научная статья по предоставленным результатам исследования и литературному корпусу.

Отбор источников внутри уже заданной коллекции разрешён как операция обработки корпуса. Инструмент не должен незаметно дополнять корпус внешними материалами.

## 2. Базовый принцип

LLM не должна сразу писать связный текст из необработанной коллекции. Рабочий процесс разделяется на четыре стадии:

1. получение и нормализация материалов из Zotero;
2. извлечение проверяемых фрагментов и фактов;
3. построение таблицы доказательств;
4. формирование и аудит ответа, обзора или статьи.

Модель не является источником. Источником считается только материал, присутствующий в предоставленном корпусе или в утверждённых исходных данных исследования.

## 3. Zotero MCP как штатный вход

Zotero MCP считается уже установленным компонентом и не является предметом выбора между альтернативными MCP-серверами. В тестах оценивается то, как последующие компоненты обрабатывают полученные через него данные.

Для каждой публикации желательно получать:

- `zotero_item_key`;
- название, авторов, год и идентификаторы из записи Zotero;
- принадлежность к коллекциям;
- HTML полного текста;
- PDF или ссылку на вложение при наличии;
- заметки, аннотации и выделения;
- тип и язык документа.

HTML является предпочтительным представлением для первичного теста: он сохраняет заголовки, абзацы, списки, таблицы и ссылки без дополнительного разбора PDF. PDF используется для сверки страниц, рисунков, сложных таблиц и материалов без полноценного HTML.

## 4. Нормализованная модель источника

Каждая публикация получает стабильный `source_id`. Минимальная запись корпуса:

```yaml
source_id: SRC-0001
zotero_item_key: ABCD1234
title: "..."
content_type: html
content_hash: "..."
sections:
  - section_id: sec-methods
    heading: Methods
    text: "..."
locators:
  html: "section#methods > p:nth-of-type(3)"
  page: 7
```

Для HTML локатор должен указывать секцию и элемент документа. Для PDF дополнительно сохраняются страница и, когда возможно, координаты фрагмента. Хэш нужен для обнаружения изменения входного текста между запусками.

## 5. Таблица доказательств

До генерации связного текста создаётся `evidence_table`. Одна строка соответствует одному проверяемому утверждению или значению.

|Поле|Содержание|
|---|---|
|`evidence_id`|стабильный идентификатор фрагмента|
|`source_id`|публикация или исходный материал исследования|
|`claim`|что именно подтверждает фрагмент|
|`verbatim_fragment`|точный фрагмент источника|
|`locator`|HTML-секция/элемент или страница PDF|
|`study_context`|дизайн, выборка, метод и условия|
|`value` / `unit`|число и единица, если применимо|
|`limitations`|ограничения применимости|
|`review_status`|машинная или ручная проверка|

Пересказ не должен подменять точный фрагмент. Для критических чисел и выводов сохраняются оба представления.

## 6. Сценарий «вопрос/ответ»

Вход:

- вопрос пользователя;
- явно заданная коллекция или перечень `source_id`;
- режим ответа: краткий, сравнительный или аналитический.

Обязательный выход:

- прямой ответ;
- список атомарных утверждений;
- ссылки каждого утверждения на `evidence_id`;
- указание противоречий и недостатка данных;
- перечень использованных источников из корпуса.

Инструмент обязан отвечать «в предоставленном корпусе недостаточно данных», если подтверждение не найдено.

## 7. Сценарий «литературный обзор»

Вход:

- утверждённый корпус;
- тема и исследовательские вопросы;
- желаемая структура и объём.

Промежуточные артефакты:

- карточки исследований;
- тематическая матрица;
- таблица методов, выборок и результатов;
- таблица противоречий;
- `evidence_table`;
- план обзора.

Итоговый текст должен:

- синтезировать публикации по темам, а не пересказывать их последовательно;
- различать результаты, интерпретации авторов и выводы составителя обзора;
- явно показывать расхождения между исследованиями;
- связывать каждое содержательное утверждение с доказательствами из корпуса;
- не расширять область вывода за пределы дизайна и выборки источника.

## 8. Сценарий «итоговая статья»

Для статьи по результатам исследования литература и данные выполняют разные роли:

- литература обосновывает контекст, состояние проблемы и обсуждение;
- протокол описывает фактически выполненные методы;
- замороженные таблицы результатов являются единственным источником чисел раздела Results;
- утверждённые рисунки и таблицы являются самостоятельными версионируемыми входами.

Обязательные правила:

1. Methods формируется только из утверждённого протокола и описания фактически выполненных процедур.
2. Results формируется только из замороженных результатов.
3. LLM не выполняет скрытые перерасчёты и не восстанавливает отсутствующие данные.
4. Каждое число связано с `result_id`, таблицей, строкой, столбцом и версией.
5. Отсутствующее значение обозначается `[ДАННЫЕ НЕ ПРЕДОСТАВЛЕНЫ]`.
6. Изменение числа, единицы, метода, размера выборки или статистического теста считается критической ошибкой.
7. Discussion отделяет наблюдаемый результат от его интерпретации и сопоставления с литературой.

## 9. Обязательные артефакты эксперимента

```text
experiment_manifest.yaml
corpus_manifest.jsonl
source_snapshots/
evidence_table.jsonl
claims.jsonl
output.md
audit_report.json
run_log.json
```

Для статьи дополнительно создаются:

```text
protocol_snapshot/
results_manifest.json
figures_manifest.json
manuscript.md или manuscript.tex
```

`experiment_manifest.yaml` фиксирует версию инструмента или skill, модель, параметры, шаблон запроса и идентификатор корпуса.

## 10. Что измеряется

### Извлечение

- полнота извлечения секций из HTML и PDF;
- точность таблиц, чисел и единиц;
- точность локаторов;
- устойчивость к сложной структуре документа.

### Вопрос/ответ

- точность ответа;
- полнота найденных доказательств;
- доля утверждений без поддержки;
- корректность ссылок на фрагменты;
- умение сообщать о недостатке данных.

### Литературный обзор

- покрытие ключевых тем корпуса;
- качество многодокументного синтеза;
- обнаружение противоречий;
- отсутствие вымышленных источников и результатов;
- прослеживаемость предложений до `evidence_id`.

### Итоговая статья

- точное совпадение чисел с замороженными результатами;
- согласованность Methods с протоколом;
- согласованность текста, таблиц и рисунков;
- корректность цитирования предоставленного корпуса;
- отсутствие добавленных методов, результатов и причинных выводов.

### Эксплуатационные характеристики

- время выполнения;
- использование памяти и вычислительных ресурсов;
- число токенов и стоимость, если применимо;
- повторяемость между запусками;
- неожиданные сетевые обращения;
- объём ручных исправлений.

Инструмент или skill, которому для основной логики необходим внешний LLM/API, не допускается к корпусному benchmark. Если необязательные сетевые функции можно полностью отключить и проверить это наблюдением за процессом, тестируется только локальная конфигурация.

## 11. Уровни тестирования

1. **Компонентный тест:** одна операция над одной публикацией.
2. **Корпусный тест:** вопрос или извлечение по нескольким публикациям.
3. **Workflow-тест:** полный путь до одного из трёх допустимых выходов.
4. **Регрессионный тест:** повторение эксперимента после обновления инструмента, модели или skill.
5. **Слепая экспертная оценка:** сравнение нескольких систем без указания их названий рецензенту.

## 12. Первый пилот

Первый корпус целесообразно составить из 20–50 открытых статей, уже добавленных в отдельную коллекцию Zotero. В него должны входить:

- статьи с полноценным HTML;
- обычные текстовые PDF;
- PDF со сложными таблицами и рисунками;
- несколько публикаций с согласующимися результатами;
- несколько публикаций с явными противоречиями;
- заранее подготовленные эталонные вопросы и фрагменты доказательств.

Первым сравнивается простой baseline «Zotero MCP → HTML → один агентный проход» с конвейером «Zotero MCP → структурированное извлечение → evidence table → отдельная генерация → аудит».
